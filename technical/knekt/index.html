knekt

the kernel

knekt is the kernel core. most of what the kernel does lives in the named parts around it. knekt is the piece that wires them together.

boot

GRUB boots the kernel through Multiboot into a short piece of hand-written assembly, which sets up just enough of the machine to call knekt's main. main wakes the machine a piece at a time, the serial port, the framebuffer (punkt), the keyboard, memory (jenna), the interrupt table and the timer. then it tiles the screen into windows (kakel), starts a shell in each (skalman) along with the scheduler (chrone). it brings up the filesystem (jakel).

when things go wrong

a fault in a ring-3 program ends that program. a fault at a guarded user-copy instruction releases the calling program's temporary kernel resources and ends that program through a separate abort path. recovery requires a matching active transfer and saved kernel frame, so an arbitrary kernel fault cannot take this path. outside the authorized boot probe, other kernel faults print a diagnostic over serial and halt. a fixed capacity in the kernel that fills up says so on the serial port rather than dropping work without a word. the serial line takes one whole log line at a time. what a program prints reaches it as whole lines too, so a timer tick or another program never cuts a line in two.

ring 3

programs are static elf64 executables, usually read from jakel. each runs in ring 3 with page tables, a kernel stack and a heap of its own. each talks to the kernel through the syscall instruction. in coff's --elf mode a program reaches them through builtins such as win_info() and readfile().

a program's code can be run but never written. its data, heap and stack are written but never run. a program that makes machine code, like utsikt's glimt, asks SYS_PROTECT to turn a page read-only and runnable first, so no page is both at once. the kernel refuses to start a program with a segment that can be both written and run.

user memory

a system call checks the whole byte range it will consume before drawing, changing a file or starting another program. the range must fit without overflow and belong to the caller's mapped pages. every level of the page tables must allow user access, with write permission when the kernel will write. a reserved heap address without a mapping does not pass this check. bounded text is copied once and stops at its first zero byte or capacity. a range that wraps around or is negative is refused. a program that asks for one is stopped while the kernel goes on.

preflight and transfer run with interrupts off on one processor, keeping the mappings stable between the check and the access. copies use registered assembly instructions with a bounded abort path. a fault during an accepted transfer ends the caller and releases its temporary storage. file growth keeps the old storage and metadata until the copy succeeds. bytes already written to an existing file or framebuffer are not rolled back after such a fault.

the drawing calls take coordinates relative to the program's own window. a program draws a whole frame into its own buffer and shows it with one SYS_PRESENT, which is also why SYS_GLYPH hands over a font bitmap instead of drawing text. keys reach a program only while its tavla has focus, through a queue of its own.

SYS_OPEN to SYS_CLOSE, 23 to 26, are ordinary files, eight open at a time per program. in --elf mode coff turns open_read, open_write, read, write and close into them, so a program written for files on linux runs here unchanged. a path starts from the folder the program was started in, or from the root when it begins with /. coff and smed are two such programs. moonshot carries both. it builds a program on its own, with the shell's execute or step by step. 

start coff.elf --elf hello.c0 hello.s
start smed.elf --base 0x80000000 hello.s hello.elf
start hello.elf

the hello.s coff writes on moonshot is the same, byte for byte, as the one coff writes on linux.
